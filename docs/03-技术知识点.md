## A. 语料工程：把聊天记录变成可用数据

### A1. 多种来源的统一解析

**用在**：`chatlog.py`

聊天记录的来源五花八门：电脑版导出的 txt、csv、手机导出的 json，以及**只能截图的情况**。
做法是先归一到统一的 `Record(sender, kind, text, ts)`：

- 按行/按字段嗅探格式，识别"我:" / "对方:" 这类说话人前缀
- `kind` 分三类：`text`（真正要用的）、`media`（图片语音占位）、`system`（软件提示）
- **只有 `text` 参与风格统计和人格生成**

### A2. OCR 提取与噪点治理

**用在**：`tools/ocr_chat_images.ps1`、`feeder.py`

截图走 Windows 自带的 OCR（`Windows.Media.Ocr`），不需要联网也不装第三方库。但 OCR 出来的文本有三类系统性噪声：

| 噪声 | 例子 | 处理 |
| --- | --- | --- |
| 字间空格 | `你撤回 了一条消息` | 比对前先做空格归一化 |
| 识别失败的字 | `海生取（0乃`、`III` | 用汉字占比阈值过滤整条 |
| 笔画被认成符号 | `II 0 |`、`23： 巫` | 过滤纯字母数字串 |

**关键教训**：OCR 噪声不会以"明显的乱码"出现，它会伪装成**高频词**。
`III` 在语料里出现 27 次，一度被统计成"第三大口头禅"写进了提示词。
所以过滤必须在**统计之前**，而不是在生成之后。

### A3. 系统消息过滤（一个典型的隐蔽 bug）

**用在**：`chatlog.py` 的 `SYSTEM_HINTS`

聊天软件会插入自己的提示："你撤回了一条消息，你猜猜撤回了什么"。
经过 OCR 之后它看起来像一句正常的聊天内容，于是被当成"她说过的话"——
结果是 **"你猜猜撤回" 成了她最有辨识度的口头禅**，因为它在语料里高频出现。

修复方式是在解析阶段就把这类行丢掉，匹配时**先去掉空格再匹配**
（`你撤回 了一条消息` 也要能命中）。这一个修复让语料少了 11 条污染记录。

## B. 语言风格建模：把"像"变成可计算的数

### B1. 风格指纹的七个维度

**用在**：`style.py` → `style_report.json`

| 维度 | 实测值（示例语料） | 用途 |
| --- | --- | --- |
| 句长分布 | 均值 6.9 / 中位 5 / P90 11 | 约束生成长度 |
| 短句占比 | ≤6 字占 61.7% | 判断"该短" |
| 结尾标点 | **95.8% 不带标点** | 决定要不要加句号 |
| 逗号使用率 | 5.4% | 说明她**用空格代替逗号** |
| 语气词配比 | 吧 89 / 啊 48 / 呢 39 … | 保留人味的关键 |
| 连发节奏 | 均值 3.66 条，最长 36，67.8% 连发 | 决定拆几条 |
| 中英/数字混用 | 拉丁 4.9%，数字 7.8% | 允许自然混用 |

这些数字不是拿去给模型"看"的，而是**反过来约束生成**：拆条数、延迟、长度上限都从这来。

### B2. 口头禅提取：n-gram + 文档频次 + 子串抑制

**用在**：`style.py` 的 `_catchphrases()`

做法：

1. 对每条消息切 2/3/4/5-gram
2. 同时统计 **总频次** 和 **文档频次**（出现在多少条消息里）——后者更重要，
   因为它能排除"一句话里重复刷屏"造成的虚高
3. 排序权重 `doc_freq × (len-1) + total × 0.1`：偏长、偏分散的短语
4. **子串抑制**：如果 `笑死我了` 已入选，就不再收 `笑死我`

还要额外过滤四类：

- 语法虚词（`的了地得着之` 开头的一律不要）
- 通用功能词（什么、就是、现在、然后…）
- **聊天软件界面词**（聊天记录、设置、朋友圈、联系人…）——截图识别最容易带进来
- **纯字母数字串**（`III`、`cos`）——加了汉字门槛才挡住

### B3. 为什么"学策略"比"学句子"重要

早期版本把语料检索结果直接塞给模型，结果它**照抄原句**：
问第二次同样的问题，回答和第一次一模一样。

改成两层：

- **句子层**：语料只用来统计，不直接进上下文
- **策略层**：让人格档案里出现"遇到什么情况会怎么表达"的规则，例如
  `被要求正经表态 → 用玩笑岔开`、`被追问细节 → 用"你管我"卡住`

这一改是质量的分水岭：模型不再有句子可抄，只能按策略现场组织语言。

## C. 人格档案与提示词工程

### C1. 启发式统计 + 大模型语义分析的合并

**用在**：`persona.py`

- **本地统计**给出"怎么说"：句长、标点、连发、语气词——客观、稳定、不花钱
- **大模型**给出"什么人"：性格、幽默方式、情绪模式、价值观、边界——需要语义理解
- 合并时按字段分工：口头禅**只信模型给的**（本地 n-gram 会把界面词、歌词当口头禅）

### C2. 提示词的分区与权威顺序

最终渲染出的系统提示词约 1.5 万字节，结构固定：

```
# 这个人是谁（最高优先级的背景）
# 一句话印象
# 性格特点 / # 语气
# 表达策略（最重要，学的是这些，不是句子）
# 回复节奏
# 真实示例（只看"策略"那一栏，回复本身不要照抄）
# 在意的点 / # 语言习惯 / # 话题 / # 关系差异
# 语料统计（供参考，不要背出来）
# 硬性规则 1-13
# 输出格式（必须严格遵守）
```

几个踩出来的经验：

1. **规则要编号**，模型才知道"第 7 条"指的是什么
2. **权威顺序要写死**："现实背景 > 记忆摘要 > 语料"
3. **不要把内部渲染符号写进提示词**——用了 `｜` 当分隔符，模型学着在回复里也加 `｜`
4. 规则里的语气同样重要：写"宁可平淡也不要答非所问"会让回复变干，
   所以补了一句"逻辑是底线，但不能为了求稳把话说干"

### C3. 输出格式即约束

把输出从"一段文字"改成结构化的多条消息：

```json
{"messages": ["第一条", "第二条", "第三条"]}
```

这一个改动同时解决了三件事：连发不再靠模型自觉、拆条有了明确边界、
平台侧能按数组逐条渲染成"真人连发"的效果。

**坑**：DeepSeek 的 JSON 模式要求对话**出现过 "json" 字样**。
历史里有 assistant 消息时，只在 system 里说明会直接返回空内容，
必须在最后一条用户消息上再补一句格式提示（详见 04-踩坑第 1 条）。

## D. 检索：BM25 而不是向量库

**用在**：`retriever.py`

选择理由：

- 数据规模小（几百组对话，几万字），BM25 足够
- 中文短句场景下，词面匹配比语义向量更可控——不会"联想"出不相关但意思相近的句子
- **零依赖**：纯标准库实现，不需要模型服务、不需要 GPU、不需要下载几百 MB 的词表

最终在稳定版本里**默认关闭**：不是 BM25 不好，而是"给模型真实例句"这件事本身
会诱发照抄。现在它作为可选能力保留（`retrieval.enabled`），
开启时提示词会明确写"只学语气和节奏，不要照抄句子"。

## E. 记忆系统

### E1. SQLite 三张表

```sql
msgs(id, chat_id, role, sender, content, ts)   -- 对话原文
facts(id, chat_id, fact, ts)                   -- 长期事实（含【修正要求】）
kv(k, v)                                       -- summary:<chat_id> / summary_id:<chat_id>
```

选择 SQLite 而不是 JSON 文件：并发写安全、可以按 chat_id 和时间查询、天然支持增量。

### E2. 记忆污染——本项目最重要的一个认知

**现象**：改了提示词之后，机器人**仍然**坚持说自己在"上计算机导论"。

**根因**：它的长期摘要里已经写进了这句话。

```
summary:<chat_id>
  … 对方问我在哪，我说在机房上计算机导论，老师在念PPT …
```

每一轮，这段摘要都会作为背景重新喂给模型。模型读到"我自己说过在上课"，
就把它当成既成事实继续往下编。**提示词的正确性输给了上下文里的事实性。**

由此得到三条规则（已写进代码）：

1. 生成后要做**程序化**校验，不能只靠提示词
2. 摘要生成时**禁止记录"我此刻在做什么"这类会过期的状态**
3. 历史消息里和当前阶段矛盾的条目，进上下文前就要**过滤掉**

### E3. 摘要的滚动策略

每 12 条消息触发一次压缩，输出 5-8 行、上限 900 字；压缩时把旧摘要一起喂进去做合并。
存库前用当前阶段的禁忌词再过一遍，矛盾行直接丢弃。

## F. 现实感知：让它活在"现在"

### F1. 时间感知

**用在**：`clock.py`

8 个时段（凌晨/清晨/上午/中午/下午/傍晚/晚上/深夜）× 4 种阶段文案
（`training` 军训 / `preterm` 待开课 / `term` 上课 / `break` 假期）。

为什么必须按阶段分？因为**通用文案会和现实打架**：
原来的"上午"提示词写的是"上午一般在教室上课"——
这句话在军训期间直接教模型说自己在教室。修掉之后，"上午"变成
"上午在军训——站军姿、走方阵，太阳底下晒着，回消息又慢又短"。

另外还有"夜猫子"变体：同一个人熬夜和不熬夜，深夜的表现完全不同。

### F2. 校历状态机

**用在**：`reality.py`

把学期抽象成状态机而不是硬编码日期判断：

```
注册 → 军训期（9/7-9/24） → 待开课（9/25-9/27） → 上课第 N 周 → 期末 → 寒假
```

每个状态决定：当前阶段描述、近期关键日期（军训还剩几天、什么时候开课）、
作息表、以及**禁忌词表**。

### F3. 节假日数据

**用在**：`reality.py` + `data/holidays.json`

法定节假日是**国家统一规定**的，不是"等通知"的东西。所以特意接了放假安排数据
（公共 API 抓一次，缓存成本地 JSON，共 72 条记录），并且在提示词里明确写：

> 法定节假日（春节、清明、劳动、端午、中秋、国庆、元旦）的放假日期是国家统一规定的，
> 早就定好了。被问到这些，直接说日期和天数，**绝对不能回答"还没通知""看放不放"**。

这一条直接对着一个真实翻车：问"国庆放不放假"，它答"得看学校通知"——
把常识题答成了不确定题，显得很笨。

### F4. 元知识：知道自己"不知道什么"

放假安排每年 11 月才公布**下一年度**的通知。所以当日期超出数据覆盖范围时，
正确回答是"还没公布"，而不是编一个日期。

实现上给提示词加了一条动态说明：

> 注意：10 月 10 日之后的放假安排国家还没公布（每年 11 月才发下一年度的通知）。
> 被问到元旦、春节这类还没公布的日子，说"还没公布、等通知"就是对的，不要编日期。

**这是很容易漏掉的一层**：模型知道自己知道什么，但不知道自己不知道什么。

## G. 输出质量保障：四道防线

### G1. 第一道：提示词里的硬性规则（13 条）

覆盖逻辑连贯、不编造、不复述问题、不装不知道、语气底线等。属于"请模型注意"。

### G2. 第二道：生成后质检（LLM-as-judge）

**用在**：`engine.py` 的 `_review()`

把「对方刚说 + 她准备发的回复 + 确定知道的事实 + 当前阶段禁忌」交给模型，
按 10 条清单逐条审，命中就重写。10 条清单：

```
1 答非所问   2 逻辑断裂   3 碎片乱码   4 复述问题   5 身份/时间不符
6 机械重复   7 编造细节   8 明明知道却装不知道   9 把法定节假日说成不确定
10 时间线错位（军训期间说自己在上课…）
```

特意加了"宁可放过，不要误改"和"重写后要更像她，而不是更不像"——否则质检会把语气改没了。

### G3. 第三道：程序化硬约束（关键）

**用在**：`reality.py` 的 `find_claims()` + `engine.py` 的 `_enforce_reality()`

因为提示词和质检**都挡不住**记忆污染，所以加了一层纯代码的校验：

- 当前阶段不允许出现的说法（军训/待开课期间：上课、下课、机房、教室、讲台、PPT、讲课、还得上、有课）
- 再加上**课程名**，但只有被说成"正在上"才算违规（`find_course_claims`：
  命中词前 6 个字里必须有 `上/在/刚/学/去/来/正在`）

**否定窗口**是个实用技巧：中文的否定和状语都在前面，
所以命中位置**前面 5 个字**里出现 `没/未/别/才/以后/等/将/不用/不会` 就放过。
这样"还没开始上课""放假不用上课""要到 9 月 28 日才上课"都不会被误伤。

命中后的处理是三级降级：**强制重写 → 丢弃矛盾的那几条 → 退回符合阶段的兜底话术**。

### G4. 第四道：重复检测

用 **2-gram 的 Jaccard 相似度**（阈值 0.55）比对最近两轮的回复，
太像就要求换一种反应重写。

选择 bigram 而不是编辑距离的原因：中文短句里"换了个说法但意思一样"的情况，
bigram 交集能抓住，而编辑距离会认为它们完全不同。

### 另外还有文本清洗

`_sanitize()`：全角空格折叠、连续空格归一、剥离 markdown 痕迹、
去除行首的"回复："前缀、把内部渲染用的 `｜` 转成换行、
`_smells_ai()` 检测 AI 腔（"作为AI""很高兴为您"…）并触发重写。

## H. 拟人化节奏：让它"像人一样发消息"

**用在**：`engine.py` 的 `_chunk()` / `_delay()`

- **拆条**：一条回复按标点和长度上限（默认 30 字）切成 1-4 条
- **打字延迟**：按字数 ÷ 打字速度（默认 6 字/秒）计算，第一条慢、后面几条快
- **随机忽略**：8% 的概率不回（真人不是每句都秒回）
- **防风控**：每分钟上限 12 条、冷却 2 秒
- **活跃时段**：支持跨天配置（`[7, 3]` 表示早 7 点到次日凌晨 3 点）

"偶尔不回""偶尔敷衍"这类**负向行为**对真实感的贡献，可能比多写几句漂亮话更大。

## I. 协议接入：从聊天软件到我的程序

### I1. OneBot 11 协议

机器人作为 **HTTP 服务端** 接收上报：聊天软件（协议端）把每条消息 POST 到
`http://127.0.0.1:5700/onebot`，程序解析后决定回什么，再通过协议端的 HTTP API 发出去。

选"接收上报"而不是"主动轮询"，是因为轮询要么延迟高、要么空转耗资源。

### I2. 分块传输编码（chunked）

实测遇到的坑：协议端的上报用的是 `Transfer-Encoding: chunked`，
普通的 `Content-Length` 读法会**读不到 body**（表现为消息收到了但内容是空的）。

处理方式是按 chunk 解析：读十六进制长度行 → 读该长度的数据 → 读到长度为 0 结束。
解析完再统一 UTF-8 解码。这个坑在 04 文档里有完整记录。

### I3. NapCat / QQNT

QQ 侧的协议端基于 QQNT 客户端做 Hook，提供 OneBot 兼容接口。
安装后在 WebUI 里配置 HTTP 服务端口与上报地址，扫码登录即可。

需要注意：**这在协议上是"非官方"途径**，账号存在被风控的可能（见 05 文档）。

### I4. 微信路线为什么放弃

原本的方案是 `wxauto` 系列（依赖**电脑版微信 3.9** 的窗口自动化）。
2026 年 9 月实测：微信 3.9.x 客户端**登录直接被拦**，提示"版本过低请更新"，
导致整条方案失效（`wxauto` / `wxautox` / `wcferry` 全部依赖 3.9）。

结论：**依赖某个特定客户端版本的自动化方案，寿命不由自己决定**。
迁移到基于协议的方案（QQ/OneBot）之后，耦合面从"UI 布局"降到了"协议字段"，
稳定性明显提升。这也是接入层要抽象成 adapter 的现实理由。

## J. 工程化

### J1. 零第三方依赖

主流程只用标准库：`sqlite3` / `urllib` / `http.server` / `re` / `json` / `hashlib`。

好处很实在：

- 换台电脑不用装环境，不会因为某个包升级而崩
- 自检可以完全离线跑
- 只有"接个人微信"才需要可选依赖（写进 `requirements.txt` 但默认不装）

### J2. Windows 上的编码问题（踩得很实）

| 问题 | 现象 | 处理 |
| --- | --- | --- |
| 控制台 GBK | 打印中文报 `UnicodeEncodeError` | 输出统一包一层 UTF-8 writer |
| PowerShell 5.1 | 无 BOM 的 `.ps1` 按 ANSI 解码，中文全乱 | 脚本存成 UTF-8 **带 BOM** |
| `.cmd` 换行 | LF 会导致批处理解析异常 | 存成 CRLF |
| 管道残渣 | 字符串里混进非法代理字符，存库/发模型直接崩 | `sanitize.clean()` 入口过滤 |

### J3. 离线自检（selftest）

`python run.py selftest` 用 mock 模型跑完整链路，共 10 项：
解析聊天记录 / 消息类型识别 / 风格统计 / 对话片段构建 / 语料检索 /
人格档案生成 / 回复生成+记忆 / 长期记忆 / 敏感话题拦截 / 企业微信加解密。

### J4. 真机验证的纪律

任何涉及发送的测试都走演练模式（`run.py qq --dry`）：
会真的收消息、真的调模型、真的组装回复，**但不发出去**，只打印"本来要发什么"。
测试完清理进程，不污染真实会话。
