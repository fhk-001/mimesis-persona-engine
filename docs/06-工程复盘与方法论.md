# 六、工程复盘与方法论

## 6.1 做对了什么

**1. 把"像一个人"拆成了可测量的指标。**
句长分布、标点习惯、语气词配比、连发节奏——这些数字本身不产生回复，
但它们让"像不像"从主观感受变成可以对照的标尺。每次改动之后能回答
"这次是更近了还是更远了"，而不是"我感觉好点了"。

**2. 分层，让方案可以整体替换。**
接入层换过三次（终端 → 微信 → QQ → 协议端），编排层和认知层一次都没改。
如果当初把发消息的逻辑写进业务代码，微信失效那天整个项目就废了。

**3. 关键约束做成了程序化，而不是写在提示词里。**
这是吃了教训之后才明白的：**提示词是建议，代码才是约束**。
阶段禁忌、摘要自净、历史过滤，全部落到 Python 里，可测、可复现。

**4. 离线自检 + 演练模式。**
改完代码跑 `selftest`（10 秒、不联网、不花钱），
真机测试走 `--dry`（真收消息、真调模型、但不发出去）。
这两个机制让"高频迭代"成为可能——否则每次验证都要花钱、还怕打扰真人。

**5. 每个修复都留下了可复现的验证。**
关键词判断有 12 条用例（该拦的 5 条、该放过的 7 条），
阶段感知有跨日期取样表，记忆库有污染扫描。
**修复不能只有"我改好了"，要有"这样验证过"。**

## 6.2 做错了什么

**1. 把提示词当成万能药。**
"军训期间说自己在上课"这个问题，我前两次修复都只改了提示词，两次都没用。
真正的原因是**记忆污染 + 多源提示词自相矛盾**。
教训：**当一个 bug 在同一类修复下反复出现，就要停止改文案，去查数据流。**

**2. 换汤不换药的"打补丁"。**
用户的原话是"你不要只针对我说的哪几句话导致的逻辑不通，换汤不换药的"。
当时我一直在给具体句子加规则，而正确做法是改机制
（数据源、注入位置、校验时机）。**针对症状打补丁的成本是指数增长的。**

**3. 派生数据没有版本意识。**
风格报告和语料示例比语料清洗逻辑晚出生了两个小时，结果提示词里
挂着 `III` 当"第三大口头禅"。这类问题的隐蔽性在于：
**代码是对的，数据是旧的是没人会发现的**。

**4. 约束只写了正面，没写边界。**
为解决答非所问写的一堆"要严谨"，直接把回复变成了客服腔。
任何约束都应该同时写清"不要越过哪条线"。

## 6.3 三条方法论

### 方法论一：上下文里的错误会被当成事实

这是整个项目最重要的一条。

模型的判断依据不是"谁说得更权威"，而是"什么更像既成事实"。
当记忆摘要里写着"我说在机房上计算机导论"，而系统提示里写着"你在军训还没开课"，
模型倾向于相信自己**说过的话**——因为那是"发生过的事"，而规则只是规则。

推广到任何带记忆的 LLM 应用：

- **写入记忆之前就要做校验**，不能等读出来再补救
- 记忆、摘要、历史，都要当成"可疑数据源"对待
- 提示词里的"事实"和"规则"要分开表述，并且明确冲突时的优先顺序

### 方法论二：先定位数据源，再改逻辑

同一个 bug 第二次出现时，不要再改上次改过的地方。
应该按数据流从源头往回查：

```
用户看到的错误输出
  ← 模型生成
    ← 上下文（这里有没有自相矛盾的信息？）  ← 这次就是在这里找到根因
      ← 记忆库 / 摘要 / 语料 / 提示词模板
```

这次之所以能定位，靠的是三件事互相印证：**运行进程的启动时间**（证明代码是新的）、
**记忆库里的原文和时间戳**（证明污染存在）、**提示词渲染的实际文本**（证明模板自相矛盾）。

### 方法论三：每个修复都要有"离线可复现的验证"

不能依赖"跟真人聊两句看看"。因为：

- 真机测试花钱、打扰人、不可重复
- 主观感受无法比较"这次是不是更近了"

所以每个修复都配套一个离线用例：

| 修复内容 | 验证方式 |
| --- | --- |
| 阶段禁忌词 | 12 条关键词用例（含否定窗口的正例反例） |
| 阶段感知 | 跨 7 个日期取样，打印阶段/是否有课 |
| 记忆污染 | 扫描全库，统计"和当前阶段矛盾"的消息条数 |
| 语料噪声 | 统计示例里汉字占比异常的比例 |
| 整体链路 | `run.py selftest` 10 项 |

## 6.4 如果重做，会怎么设计

1. **记忆写入时就带"事实等级"**：把"她自己说过的话"和"系统给出的事实"分开存储，
   冲突时按等级裁决，而不是靠提示词里写一句"以现实背景为准"
2. **给派生数据加版本号**：语料变更时自动标记风格报告/示例为过期
3. **校历与节假日抽成数据文件**，不要写死在代码里（既解决脱敏，也方便换学校）
4. **把"阶段"作为一等公民**：所有输出约束都挂在阶段上，而不是散落在时钟、现实、质检三个模块
5. **更早引入真机回归集**：把典型问题（军训/上课、节假日、重复提问）固化成
   一组可重复跑的真实对话，每次改动后自动过一遍

## 6.5 这个项目沉淀下来的能力

如果要写进简历，可以这样表述：

> 独立设计并实现人格化对话系统（Python，零第三方依赖，约 3400 行）：
> 从原始聊天记录出发，完成语料清洗、语言风格量化建模、人格档案生成、
> 提示词分层编排、SQLite 三层记忆、时间/校历现实感知、输出质检与程序化约束、
> 多协议接入（OneBot/企业微信/终端）的完整链路；
> 定位并解决了"上下文记忆污染导致人设时间线错乱"等系统性问题，
> 建立离线自检与演练模式保障高频迭代。

更值得强调的是**解决问题的方式**，而不是用到的名词：

- 面对"反复修不好的 bug"，能把排查范围从"改提示词"推进到"查数据流"
- 知道**LLM 应用里哪些约束必须落到代码、哪些可以交给提示词**
- 会为不可靠的模型输出设计**分层降级**（重写 → 丢弃 → 兜底）
- 对隐私、风控、成本有明确边界意识，而不是"能跑就行"
